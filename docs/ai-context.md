# Промпт восстановления контекста

Привет! Мы продолжаем переписывать приложение PixelTerminalUI (https://github.com/alexeysp11/pixel-terminal-ui/blob/issue-3) на stateless/Backend-Driven UI архитектуру (.NET 8 / ASP.NET Core). 

Вот ключевые точки, которые мы уже спроектировали и зафиксировали:
1. Клиент-Сервер: Тонкий клиент общается с бэкендом по HTTP REST. Клиент шлет ввод только по Enter (посимвольный ввод в буфер строки `> ввод` происходит локально). Сервер возвращает плоский массив структур `Pixel[]` и размеры экрана.
2. Общая либа: PixelTerminalUI.Contracts содержит структуру: `public readonly record struct Pixel(char Symbol, bool IsInverted, ConsoleColor Foreground = ConsoleColor.White);`
3. Хранилище: MongoDB. Формы хранятся как Embedded-документы (Форма -> Вложенные контролы -> Вложенные команды). Полиморфизм настраивается через `BsonClassMap.RegisterClassMap`. Состояние уникально для каждого `userId` (Session).
4. Валидация: Долгоживущая (машина состояний) идет через класс `Command<TEnum>` с упаковкой в `int RawState` через `Unsafe.As`. Быстрая валидация — через stateless-делегаты в DI на бэкенде.
5. Иерархия моделей: Использованы record-типы. `BaseForm` (`SimpleMessageForm`, `ScrollMessageScreen` и др.) содержит `IEnumerable<TextWidget>` Controls. Свойства-ссылки на спец. контролы заменяются на ID (например, `TitleControlId`). Контролы: `TextWidget` -> `TextEntryWidget` -> `ComboEditControl` / `PasswordEditControl`.
6. Рендеринг: Чистая синхронная функция `Pixel[,] Draw(BaseForm form)`. Пустые места заполняются `' '`. Активный контрол (`form.FocusedEditControlId`) подсвечивается точками `'.'`. Рендерер "глупый" — он не считает логику видимости, а просто проверяет флаг `control.Visible`, который выставил бэкенд на этапе валидации.
7. Параллельные сессии (Session Isolation): если два пользователя могут работать с одной визуальной формой, то для каждого пользователя будет создан своя сессия, свой экземпляр формы и у этой формы будут свои поля, команды и внешние связи. Поэтому изменения в текстовом поле одной формы никак не должно влиять на состояние формы из другой сессии.

Когда будешь генерировать код, в коде пиши исключительно на английском (касается названий классов/методов/переменных, а также комментариев в коде). Все классы/рекорды, которые не должны иметь наследников, в обязательном порядке должны помечаться ключевым словом `sealed`. Стоит писать явные типы, избегая `var`: вместо `var t = Test(123)` используем `Test t = new(123)`. Инициализация коллекций предпочтительна с использованием квадратных скобок `[]`.

Когда пишешь комментарии, просьба не использовать цифры для обозначения шагов: например, вместо `// 1. Load the active form document from MongoDB` лучше использовать `// Load the active form document from MongoDB`. Дело в том, что при рефакторинге последовательность шагов может поменяться, и цифры собьются, что будет вызывать больше когнитивного напряжения при чтении и понимании кода.

Если будем писать тесты, то стоит придерживаться следующего стэка: xunit, FluentAssertions, Moq, AutoFixture, Testcontainers.
При использовании FluentAssertions стараемся использовать параметр `because`, который объясняет валидируемое значение. Лучше располагать на разных строчках методы `Should()`, `Be()`, etc. Если есть возможность использовать `And` для множественной валидации одного и того же объекта, то стоит использовать `And`.
```csharp
// Вместо такого:
deserializedEditControl.Command.Should().NotBeNull("because polymorphic MongoDB mapping should correctly bind embedded nested commands objects");
deserializedEditControl.Command.Should().BeOfType<CancelTasksCommand>("because MongoDB type discriminators must resolve concrete plugin command entities");

// Лучше использовать такое:
deserializedEditControl.Command
    .Should()
    .NotBeNull("because polymorphic MongoDB mapping should correctly bind embedded nested commands objects")
    .And.BeOfType<CancelTasksCommand>("because MongoDB type discriminators must resolve concrete plugin command entities");
```

В коде, поскольку ты используешь явное указание типов, то лучше использовать их с оператором `new`: используй `SimpleMessageScreen parentScreen = new()` вместо `SimpleMessageScreen parentScreen = new SimpleMessageScreen()`. Когда используешь имена типов, старайся не использовать их неймспейсы в имени (пиши `SimpleMessageScreen` вместо `YourProject.SimpleMessageScreen`).

## Текстовое поле ввода `TextEntryWidget`

Нашел информацию в доках по старому документу, как должно рабтать текстовое поле ввода `TextEntryWidget`:
- **Наследование**: наследуется от `TextWidget`.
- **Поля**: обязательно для заполнения `Required`, `Hint` (подсказка для ввода внизу формы).
- **Валидация**: валидация перед отображением `ShowValidation` (отображает поле, если оно видимое, также отображает подсказку); валидация перед отображением `RequireValidation` (допускает ввод значений в поле, если оно обязательно для заполнения); валидация ввода `EnterValidation`.

По поводу Hint примерно так должно отображаться:
```
|---------------|
| Enter name:   |   <- Обычный TextWidget
| ............. |   <- TextEntryWidget, в который мы вводим сейчас (он активный).
|               |
| Enter login:  |   <- Обычный TextWidget
|               |   <- TextEntryWidget, который не является активным сейчас.
|               |
| ENTER NAME    |   <- Hint для текущего активного TextEntryWidget
|---------------|
> Пользовательский ввод здесь
```

## Фокус в контролах

Относительно смены фокуса на контролах: пользователь вводит значение, мы обрабатываем это значение, и можем установить явным образом форму и контрол, который должен стать активным (в старой версии библиотеки я именно так и закладывал, т.е. разработчик, который использует нашу либу сам может устанавливать фокус в зависимости от введенных значений). Кроме того, глобально на уровне всей либы я завел спецсимволы, которые тоже могли использваться для навигации:
- `-q`: выйти из приложения.
    - Если пользователь действительно хочет выйти из приложения, то необходимо разорвать сессию: отправляем на клиент форму с сообщением, что сессия разорвана, и в JSON отправляем флаг о выходе из приложения; в свою очередь, на клиенте при заполнении этого флага просто завершаем консольное приложение.
- `-m`: выйти в главное меню.
- `-c`: настройки.
    - Язык, логин/пароль пользователя, timezone, etc.
- `-h`: помощь/информация по всему приложению.
- `-i`: помощь/информация по текущему контролу.
- `-r`: перезагрузить текущий контрол со значением по умолчанию.
    - Реализуется <u>на уровне валидации конкретного контрола</u>.
- `-n`: далее.
    - Очень часто приравнивается к нажатию на Enter с пустой строкой.
- `-b`: назад.
- `-x`: отменить.
    - В большинстве случаев эквивалентен комбинации `-b` (на данный момент не используется активно).
    - При использовании `ComboEditControl` символ `-x` означает выход из контрола и переход назад, а символ `-b` - пролистнуть назад список вариантов для выбора.
- `-s`: сохранить.
    - При использовании `ComboEditControl` данный символ означает, что в режиме `MultiSelectEnabled` пользователь выбрал все интересующие его варианты.

Для понимания legacy контекста: в wms была логика, где мы для такого кастомного порядка использовали свойства контролов ReadOnly/Visible, а также вручную ставили фокус на контрол (вроде на форме было свойство FocusedControl, который и опредлял фокус). В старой реализации своей либы я тоже делал примерно так же:
```csharp
private bool txtUserInput_EnterValidation()
{
    try
    {
        switch (txtUserInput.Value)
        {
            case "":
            case "-n":
            case "-b":
                SessionInfo.CurrentForm = ParentForm;
                return true;
            
            default:
                FocusedEditControl = txtUserInput;
                return false;
        }
    }
    catch (Exception ex)
    {
        ShowError(ex.Message);
        return false;
    }
    finally
    {
        txtUserInput.Value = "";
    }
}
```

Но библиотека также должна уметь делать навигацию на основе "зашитых" спецсимволов. И может получиться следующая ситуация: на форме контролы должны переключаться `control a -> control b -> control c`, мы находились на `control c`, ввели `-b` и должны оказаться на `control b`, а не совсем уйти с формы. Если введем ещё раз `-b` и должны оказаться на `control a`. И только находясь на `control a`, мы вводим `-b` и попадаем на родительскую форму.
Если мы находимся на `control a`, и ввод не `Required` (допускает пустой ввод), то переходим на `control b`.
